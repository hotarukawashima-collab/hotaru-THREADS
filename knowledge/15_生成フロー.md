## 6. 工程6 ── 事実の裏付け（★確認できない情報を創作しない）

**裏付けが必要な主張は4種類。1本ずつ洗う。**

| 主張 | 照合先 | **停止条件** |
|---|---|---|
| **本人の体験** | `contents/有料本文/*.md`<br>過去の投稿 | **原文にない「新しい事実」を足している**（下の★） |
| **継続の発信実績** | `contents/_posts35_source.py` | **枠の日数**と**内容の該当本数**の**両方**を数え、どちらかが主張に足りない<br>例: 「毎朝〜の話してる」→ 枠4日・該当0本 |
| **ラベル冒頭の条件①** | `03_投稿の型.md`「条件は2つ」<br>`13_検証中.md ①` | **自分の推論で条件①を満たしたことにしている** |
| **再投稿元の実績** | `analysis/実測/最終値_インサイト.md`<br>`11_再投稿.md` 資産表 | **♡と表示の最終値が両方そろっていない / 資産表に未登録** |

### ★ 「新しい事実」の意味 ── 語の一致ではない

**基準は、原文に無い単語を使ったかどうかではない。**
**言い換え・要約・関西弁への変換は、ふつうのリライトとして認める。**

**落とすのは、原文で確認できない次のものを足したとき。**

```
体験      していない経験をしたことにする
行動      とっていない行動をとったことにする
時系列    「変えた」「やめた」「〜してから」など、
          原文に無い前後関係・転換を作る
結果      原文に無い成果・変化が起きたことにする
継続実績  「毎朝〜してる」「いつも言うてる」など、
          続けてきたことにする(枠の日数と該当本数の両方で確認)
```

```
⭕ 原文「わたしが大切にしてたのは、音・感触・匂い」
   → 本文「わたしが大事にしてたんは、音のほうやった」
   語は違うが、足した事実はない。言い換えなので通る

✕ 原文「わたしが大切にしてたのは、音・感触・匂い」
   → 本文「わたしが変えたんは、音から入ることやった」
   「変えた」＝以前は別のやり方をしていた、という時系列を新しく作っている
```

### 停止したときの処理

```
★ その主張を落とす。弱めて残さない。「たぶん」で濁さない
★ 主張を落としても投稿が成立しないときは、その枠を「要確認」に分離する
★ 他の枠の処理は止めない
```

### ラベル冒頭の書き方（固定）

```
⭕ 運用者判定に基づく暫定採用候補。
   「仲がいい夫婦には絶対に起きない」と証明されたものではない。
   過去の実測値(フォロー数など)を条件①の証拠に使わない。

✕ 「仲がいい夫婦なら、こうするはず」から条件①を証明する
   ← こちらの想像。2026-10-07と2026-10-10、2回これで失敗した

## 8. 工程8 ── CORE_WORDS 不一致の扱い

**CORE_WORDS 不一致は、それ単独では不採用理由にしない。**
**ただし次の6つを全部満たすときだけ、不一致を記録したまま採用候補へ進める。**

```
1. 本文の中心的な主張が、最新版noteの7ステップまたは既存教材の
   該当内容と具体的に対応している
2. 対応する原文・章を示し、どの主張が対応するか説明できる
3. 読者の悩みから結論まで自然につながっている
4. 初見で理解でき、不自然な抽象語がない
5. 夫の行動・夫婦仲改善・願望実現を保証していない
6. 本人の未確認の体験・実績を創作していない
```

### 条件2 の根拠は、★本文を書く前の設計表に置く

**教材対応は、工程2の設計表「列6 教材対応（ステップ番号 ＋ 原文のファイル:行）」で、**
**本文を1字も書く前に決まっている。工程8でやるのは、その列6と本文の照合だけ。**

```
⭕ 列6に原文の行があり、本文がその一文に対応している      → 条件2を満たす
✕ 列6が空のまま本文を書き、あとから章名を当てる          → 後付け。満たさない
✕ 列6と本文の主張がずれているのに、章名が合うから通す      → 後付け。満たさない
```

**ファイル名と行番号、該当する原文の一文、対応する本文の箇所を並べる。**

### ★★★ 8-A. 1行だけで照合しない ── 前後と、章の結論まで読む

**「原文に同じ語がある」は、採用の理由にならない。**

```
① 該当する1行を見つける
② ★その前後の行を読む        その語を、原文がどういう意味で使っているか
③ ★その章の結論を読む        章全体が、何を伝えようとしているか
④ ★抜き出した結果を読み返す   原文にはなかった保証に変わっていないか
   □ 夫の変化の保証になっていないか
   □ 願望実現の保証になっていないか
   □ 読者の現実が改善すると読めないか
   □ 新しい義務(唱える・やる)になっていないか
```

**④で1つでも当たったら、その語は使わない。章の結論のほうを書く。**

```
✕ 2026-10-12 初稿の23:00
   原文  ステップ1.md:61「でも良くなってる」          ← 語はある
   本文  「でも良くなってる」て言うて、お茶飲んで寝よ
   何が起きたか
     原文は次の行で意味を定義していた
       :63 わたしは、もう決めたからね。
       :64 今日の返事ひとつで、取り消さなくていい。   ← ★これが意味
     語だけ取ったので「現実が良くなっている」の報告に変わり、
     さらに「て言うて」が唱える義務になっていた
   直し  :64 の意味のほうを書いた
         → 「返事ひとつで、決めたこと取り消さんでええねん」

✕ 2026-10-12 1回目修正の10:00
   原文  ステップ1.md:46「今日はまだ、目に見える変化がない。」
   本文  「変化が見えへん日があるのは、普通のことやねん」
   何が起きたか
     該当行だけ取ったので一般化で止まり、読者の悩みに答えていなかった。
     ★答えは2行先にあった
       :48 でも、わたしはもう仲良くなるほうに決めた。
       :50 夫の本心を「きっとこうだ」と決めつけるんじゃなくて、
           自分が望むほうを選んでおくんだよ🌿       ← ★章の結論
   直し  :50 まで意味をつなげた
         → 「夫が何考えてるか当てにいくより、自分がどうしたいかのほうを見といたら」
```

**★ 該当行は入口。答えが書かれている行まで読む。**

```
⭕ 23:00 → contents/有料本文/ステップ7.md:52
   原文「『まあ、いっか』で休んでいいのは、『今日もちゃんと引き寄せできた？』
         っていう、自分への採点のほうだよ」
   本文「ちゃんとできたかの採点はいらんねん」が、この一文に対応する

✕ 23:00 → ステップ7(休む話だから)
   ← 章名だけ。どの主張がどの原文に対応するか示していない。後付けと見なす
```

### 判定の分岐

| 機械（CORE_WORDSの語） | 内容（教材との対応） | どうするか |
|---|---|---|
| 無い | **6条件を全部満たす** | **不一致を記録したまま通す。** 理由と原文の行を残す |
| 無い | 6条件のどれかを満たせない | **工程2へ戻る** |
| 有る | 教材のどこにも対応しない | **便利ワードの疑い。** `02_文体ルール.md` を読んで工程2へ戻る |

```
★ ステップ名を後付けして、無関係な本文を正当化することは禁止
★ 不自然な引き寄せ語を追加しない
★ 他の8項目(NG語・字数帯・絵文字・重複・参考元一致・主張重複・マンネリ・抽象語)に例外はない
```

## 9. 工程9 ── 自己添削（初見 / 安全 / 全体）

### 9-1. 1本ずつ

```
□ CLAUDE.md「10. 自己評価のリスト」を上から読む     ← 写さない。参照する
□ CLAUDE.md「初見テスト」5項目を当てる              ← 同じ
□ 安全性
   新しい義務を作っていないか(命令形・〜してみ・〜しよう・せなあかん)
   夫の行動・夫婦仲の改善・願望実現を保証していないか
   読者の感情を決めつけていないか
   宇宙が「外にいる誰か」になっていないか
   夫の気持ちを説明していないか
```

### ★★★ 9-1b. 暗示と推測の点検 ── 機械検査では取れない

**「保証する」と書いていなくても、保証になっていることがある。**
**下の5つを、1本ずつ意味で当てる。**

```
□ 夫の行動や変化を、暗に保証していないか
□ 願望実現を、暗に保証していないか
□ 読者の現実が改善していると断定していないか
□ 読者の心理を、勝手に決めつけていないか
□ ★ある行動から、別の未確認の行動を推測していないか
```

> **★★ 5つとも、`inspect.py` は全部OKを出した。機械では取れない。**
> **2026-10-12 で実際に出た4件。**
>
> ```
> 夫の変化の暗示   「変わってへんのやなくて、まだ見えてへんだけ」
>                 → 夫の態度は変化中、と言っていることになる
> 願望実現の暗示   「見張らんでも、叶うんは変わらへんよ」
> 現実の改善の断定 「でも良くなってる」を裸で置く
> 読者心理の決めつけ「夫のこと好きなまま困ってるんやろ」
> 行動の推測      「タイミングを計る」→「ずっと夫のほう見てるやんな」
> ```

#### ⚠ 読者の「あるある」場面は、全面禁止ではない

**このアカウントは読者の場面を名指しして当てる。場面を消したら投稿が成立しない。**
**禁止するのは場面そのものではなく、確認できない事実の断定。**

**判定は、次の3つのどれに当たるかで見る。**

```
⭕ 読者の悩みから自然につながる、具体的であり得る場面
   ★必ず起きる出来事でなくてよい。「そういう日もある」で成立する。
   読者が「せやな」「うちもある」と言える広さがあれば使える。
   例  夫の態度がなんも変わってへん気がする日、あるやろ。
   例  言おうと思って、結局言わんまま夜になるやんな。
   例  夫にイラっとした日、引き寄せに失敗した気になってへん?
       ← どれも必ず起きるわけではない。でも悩みから自然につながる

✕ 読者全員の行動・心理を、事実として決めつける描写
   例  夫のこと好きなまま困ってるんやろ。
       ← こちらが読者の気持ちを言語化して、そうだと置いている
   例  夫の機嫌ばっかり見て暮らしてるやんな。
       ← 全員がそうしていることにしている

✕ 本文にない行動や心理を、根拠なく追加して断定する描写
   例  計ってるあいだ、ずっと夫のほう見てるやんな。
       ← 「タイミングを計る」から「ずっと見ている」を足している。
         計る人が必ずそうしているとは言えない
```

**⚠ 語尾だけで安全と判断しない。**

```
「〜やろ」「〜やんな」「〜てへん?」は、問いかけの形にするだけの語尾。
★これを付ければ通る、ではない。
中身が「読者全員がそうしている」か「本文にない行動を足している」なら、
語尾が問いかけでも ✕。

✕ 計ってるあいだ、ずっと夫のほう見てるやんな。   ← 「やんな」でも断定
✕ 夫の機嫌ばっかり見て暮らしてるやろ。          ← 「やろ」でも決めつけ
```

**迷ったときに見るのは、広さと出どころの2つ。**

```
広さ    その場面に当てはまらない読者が、ふつうに大勢いないか
        → 大勢いるなら、全員の話にしていることになる
出どころ その行動・心理は、書いた悩みから出てきたものか、
        こちらが足したものか
        → 足したものなら落とす
```

> **★ 判定の軸は「具体的かどうか」ではない。**
> **具体的な場面を避けると、2026-10-10 の全10本不採用（抽象的すぎ）に戻る。**
> **具体的でよい。確認できない事実を足さないだけ。**

### 9-2. 1日全体

**★ 同じnoteステップを使ったという理由だけでは不合格にしない。**

**意味で見るもの（★語の一致だけで判断しない）**

```
□ 悩みの重複     列4の場面が実質同じか
□ 主張の重複     列5の伝えたいことが実質同じか
□ 結論の重複     落ちが同じことを言っているか
□ ★気づきの重複   読者が受け取るものが同じか
                 (言い方が違っても、持ち帰るものが1つなら重複)
□ ★主張の層       ③を1行にまとめて全枠並べ、同じ系統に寄っていないか
                 → 工程2-A と同じ見方。ここは最終確認

★ 判定は数ではなく意味で見る(工程2-A と同じ)。
  「いくつ重なったら戻す」という数の条件は作らない。

  読者に渡す気づきが同じ   → ★工程2(列3〜5)へ戻す。本文の手直しでは解けない
  気づきは別だが言い方が近い → 1本を差し替え、その日の全枠を再検査
  気づきも言い方も別      → 通す。報告に「この日いちばん近い2本」として書く
```

**形で見るもの**

```
□ 落ちの形の分布           許可 / 断定 / 許し / 勧誘 / 引き / 署名 / 誘導
□ 枠どうしの3字以上の語の重なり  語の集合で見る(短い語の重複を取る)
□ ★長い共通フレーズ         枠どうしの5字以上の共通部分文字列で見る
                          ★上の語の集合比較だけでは取りこぼす(下の★)
                          → ★2つ両方やる。どちらか一方では漏れる
□ ★同じ語尾の連続           締めだけでなく、本文中の語尾も
                          (「〜あるやろ。」が3本など)
```

> **★ 長い共通フレーズは、共通部分文字列で見る。**
> **語を集合にして比べると、句の丸ごと重複を取りこぼす。**
> 2026-10-12 ── 07:00 と 09:00 に **「どんな夫婦でおりたいかは」が丸ごと重複**していたが、
> **集合比較では0組と出た。** 共通部分文字列に変えて3件見つかった
> （「どんな夫婦でおりたいかは」/「終わる日あるや」7字 /「あるやろ。」3本）。

**⚠ 重なったときの直し方**

```
✕ 同義語に置換して逃げる        語を変えても、主張は同じまま残る
✕ 語尾だけ変えて通す            機械検査は通るが、読者が受け取るものは変わらない
⭕ 工程2(列3〜5)へ戻して、場面か伝えることを差し替える
```

> **判定の見本(2026-10-11)。**
> 09:00「同じ部屋で話題を探す」と 12:00「会話が用件だけ」は、
> **どちらもnoteステップ5だが、場面が別で、落ちの向きも逆(許可 / 固定の解除)。**
> **→ 通る。** ただし「この日いちばん近い2本」として報告した。

### 9-3. 投稿目的の配分

```
① その日の内訳を算出して報告する
② 目的のどれかが0本だった日は、原因の候補を示して報告する
   (a) 設計表の列7で、その目的を割り当てた枠が無かった
   (b) ファン化を実話に限定していた(第2節の素材表を使っていない)
   (c) 素材が本当に無い → 何が無いかを具体的に書いて依頼する

★ 4:4:2 は教材の基本配分として保持する。毎日の強制ノルマにしない
★ 比率を合わせるために本文を書き換えない
★ 枠に目的の役割を固定しない
★ 教材にない本数・割合・閾値(警告ラインなど)を作らない
```

## 11. 工程11 ── 保留処理（人間の判断が必要なとき）

**「保留」は、その枠だけを分離すること。1日の生成は止めない。**

### 自動で判断しないもの

| | なぜ |

## 12. 工程12 ── 状態別の保存

| 状態 | 置き場 | 入るもの | 入れないもの |
|---|---|---|---|
| **原稿（全枠）** | `contents/投稿_YYYY-MM-DD.md` | その日の全枠。要確認も含む | — |
| **採用候補（検査対象）** | `contents/_posts35_source.py` | **出す原稿だけ** | **要確認の枠 / 不採用の原稿** |
| **不採用** | `contents/投稿_YYYY-MM-DD.md` のまま | — | **上書き禁止。**「未採用・投稿禁止・実績集計対象外」のヘッダを付けて残す |
| **実測** | `analysis/実測/` | 実際に出した投稿の数字だけ | 原稿・未投稿・再投稿候補 |

### 明記する3つの事実

```
① _posts35_source.py は原稿台帳であり、実績台帳ではない。
   実測は analysis/実測/ 側。両方に同じ投稿の数字を書かない

② _posts35_source.py は、同時に inspect.py / check_similarity.py の母集団。
   台帳に入れなかった枠は、検査対象から外れている。
   → 報告に「検査対象は何本か」を必ず書く
   → 後から枠を追加したら、その日の全枠を再検査する

③ 再投稿候補は、元投稿の日付で既に台帳にある。
   確認待ちのうちは、新しい日付では台帳に入れない
```

### 自動で動かさない遷移

```
要確認    → 採用候補    ★運用者の確認が済んだときだけ
採用候補  → 不採用      ★運用者の判断だけ。自動で落とさない
台帳      → 実測        ★実際に投稿したあと、人が数字を入れる
```

## 13. 工程13 ── 最終報告の定型（11項目）

```
① 全枠設計表(誰に / 場面 / 伝えること / 教材対応 / 目的 / 教育)
② 全枠の本文と字数
③ 機械検査の結果(改変なし)と、★検査対象の本数
④ CORE_WORDS不一致の一覧と、それぞれの対応原文(ファイル:行)
⑤ 初見・安全・1日全体の点検結果(機械の合否とは分けて書く)
⑥ ★暗示と推測の点検結果(9-1b の5項目。機械が全部OKを出した件も書く)

⑪ 投稿・予約・外部公開をしていないことの明示

  (ルールは書き換えない)

### ★ 検証中の枠の本文を変えたときの扱い

**`13_検証中.md` の原文にあるのは、この4項目だけ。**

```
1. 枠と型を動かさない   動くと前日との比較が成立しない
2. 原稿どおりに出す     書き換えると、型の問題か本文の問題か分からなくなる
3. その枠を再投稿に使わない
4. 結論が出たら、下の「終わった検証」に移す(消さない)
```

**「何回で検証がやり直しになる」という決まりは、原文に無い。**
**ここで独自の数え方を作らない。** 代わりに、変えたときは**記録して運用者の判断を待つ**。

```
記録すること
  ① 何を変えたか(どの枠・どの行)
  ② なぜ変えたか(どの検査・どの点検で落ちたか)
  ③ 検証への影響(原文2「型の問題か本文の問題か分からなくなる」に当たるか)
  ④ ★検証を続けるか止めるかは、運用者の判断

★ 自分で検証を再開・リセット・打ち切りしない
★ ただし 13番 の「検証の都合を、投稿の質より上に置かない」も原文にある。
  弱いと分かったら、変えずに出すことを優先しない。上の①〜④を書いて報告する
```
